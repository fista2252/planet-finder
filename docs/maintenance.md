# Planet Finder maintenance v1

The existing heartbeat runs once weekly on **Monday at 17:00 Asia/Karachi**. The CLI owns the ledger and time budget. The heartbeat supplies current GitHub and CI information, evaluates one justified item, and records its outcome. A healthy run can end with `no_change`.

## Run a health check

```sh
python workflow.py maintenance --dry-run
```

Run from a checkout with Python 3.13, the dependencies in `requirements.txt`, Node.js and Git. Dry runs use a separate weekly ledger and exercise the same offline checks without claiming work. Repeating the command returns the existing ledger byte for byte. The default ledger is under `.audit-cache/maintenance/`. Use `--ledger PATH` to keep it in a persistent folder shared by the heartbeat and the isolated checkout. Keep the folder outside Git. Use a separate ledger path for a deliberate validation rerun.

The health command runs the regression suite, which covers cache and resume behavior, review persistence, input validation and failure paths. It rebuilds the pilot publication into a temporary directory and compares the generated files byte for byte against `docs/`. It checks cached report schema and prior warnings, validates the registry and backlog, and compares the search against a frozen benchmark. The ledger captures the commands, exit codes, output, wall time, input hashes and the benchmark results. An old catalog is a coverage warning. Missing dependencies, timeouts, unverifiable remote state and a dirty live checkout block work without becoming code defects.

## Heartbeat handoff

1. Verify the latest upstream commit, CI and any outstanding maintenance PRs through GitHub. If the shared checkout is dirty or a writer is active, leave it untouched. Prepare a clean `maintenance/*` branch in an isolated checkout at the verified commit. Never reset someone else's checkout. Keep the ledger path stable across checkouts.
2. Run `python workflow.py maintenance --reconcile remote.json --ledger PATH`. The scheduler supplies `remote.json` with the exact `commit` SHA, `ci_status` of `success`, the `ci_url`, and `checked_at` as an ISO-8601 timestamp with a timezone. The runner accepts a verification at most one hour old and checks that the commit matches local HEAD. When an outstanding item has been verified closed or merged, include its ID in `resolved_items`. A blocked week has a ledger entry and can stop.
3. Continue the unfinished item recorded in the ledger. Otherwise pick a reproduced bug first. If health checks are clean, consider only the highest-priority validated backlog item. The registry's proposed items describe research questions. The initial backlog contains no validated technique ready for implementation. A future registry transition requires recorded evidence, primary references, license verification for reused material, a baseline and prespecified acceptance criteria.
4. Before editing, reserve an attempt with `python workflow.py maintenance --action claim --ledger PATH --item BUG-123 --evidence reproduction.json`. A bug reproduction JSON supplies `reproduction` and `observed_failure`. For a validated registry item use its exact ID and summarize the evidence for selecting it. One item and at most two attempts fit in the 30-minute window, starting with the health run. Subprocesses have timeouts and an expired attempt cannot be marked ready. The heartbeat must stop its own external commands and edits by the same deadline.
5. Measure the unchanged baseline and reproduce the defect before editing. Use a focused regression and re-run relevant checks. For a scientific technique use an experimental option, document any threshold changes with a scientific rationale, and compare against the same frozen benchmark plus any independently reserved validation inputs. Preserve original data and attribution. Avoid broad surveys, paid compute and mass downloads.
6. Run `python workflow.py maintenance --action finish --ledger PATH --evidence attempt.json`. Record `disposition` as `retry`, `checkpoint`, `blocked`, `ready_for_review` or `no_change`. Include lists named `changed_files`, `tests`, `limitations` and `links`. For `ready_for_review`, include the new `benchmark` JSON from `python maintenance_benchmark.py`, passing tests and evidence or PR links. New techniques also require `experimental_option: true`. Record observed costs and checkpoint notes when available. A second retry becomes a checkpoint. The runner neither creates PRs nor applies changes. The heartbeat or maintainer presents the tested change for review and posts the CLI digest with the ledger and any PR link.

The ledger lock prevents overlapping maintenance writers that use the same path. If an interruption leaves `.maintenance.lock`, verify the process has exited before removing it. An unresolved PR carries forward as `awaiting_review`. Missing GitHub access can be recorded without retries or permission changes. The CLI relies on the scheduler's verified remote record and cannot authenticate that record independently or enforce timeouts on unrelated processes.

## Benchmark and backlog

The versioned definitions, technique registry, prioritized backlog and baseline are in [maintenance_specs](../maintenance_specs/). The public benchmark covers sparse multi-year harmonics, transit gaps, alternating eclipses, dilution, correlated noise, and white and correlated no-signal controls. It reports recovery, wrong periods, abstentions, ambiguity, false alarms, wall and CPU time, and peak process RSS where the platform exposes it. Cached reports supply a separate real-data check without rerunning network queries. The version 1 synthetic validation cases are fixed and public. A later technique evaluation must reserve a separate validation set before tuning.

Keep rates attached to their denominators. A measured period within the fixed tolerance counts as recovered. An unresolved period counts as abstention. The gap and eclipse checks are safety gates. The initial baseline is small and does not estimate survey performance or confirm a planet. Benchmark regressions block readiness, including a loss of recovery or an increase in wrong periods or false alarms. A new benchmark definition requires its own baseline and a documented comparison.
